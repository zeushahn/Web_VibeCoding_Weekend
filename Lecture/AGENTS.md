# AGENTS.md

## 1. 프로젝트 목적

이 프로젝트는 비IT 재직자가 AI 코딩 도구를 활용하여 실무에 필요한 웹페이지를 만드는 Vibe Coding 프로젝트입니다.

가장 중요한 목표는 복잡하고 전문적인 시스템을 만드는 것이 아니라 다음 조건을 만족하는 웹페이지를 완성하는 것입니다.

- 사용자가 쉽게 이해하고 사용할 수 있어야 합니다.
- 코드는 가능한 단순해야 합니다.
- 초보자가 나중에 수정하기 쉬워야 합니다.
- 한 번에 많은 기능을 구현하지 않습니다.
- 기존에 정상 동작하는 기능을 최대한 유지합니다.
- 화면에서 직접 결과를 확인할 수 있도록 합니다.

---

## 2. 사용자의 개발 수준

사용자는 전문 개발자가 아닙니다.

HTML, CSS, JavaScript, IndexedDB 또는 프레임워크에 대한 지식이 부족할 수 있으므로 다음 원칙을 따릅니다.

- 전문 개발 용어를 최소화합니다.
- 필요한 경우 개발 용어 뒤에 쉬운 설명을 덧붙입니다.
- 사용자가 기술을 선택하도록 요구하기보다 적절한 기본안을 제시합니다.
- 복잡한 아키텍처나 디자인 패턴을 먼저 도입하지 않습니다.
- 불필요한 라이브러리와 패키지를 추가하지 않습니다.
- 사용자가 요청하지 않은 기능을 임의로 확대하지 않습니다.

설명이 필요한 경우 다음과 같이 설명합니다.

나쁜 예:

> SPA 구조이므로 상태관리를 위해 전역 Store를 구성하겠습니다.

좋은 예:

> 여러 화면에서 같은 데이터를 사용해야 하므로 데이터를 한곳에서 관리하도록 구성하겠습니다.

---

## 3. 작업 기본 원칙

작업은 다음 순서로 진행합니다.

요청 이해 → 현재 코드 확인 → 작은 단위 구현 → 실행 → 오류 확인 → 화면 확인 → 수정

한 번에 전체 프로젝트를 크게 변경하지 않습니다.

가능하면 하나의 요청을 작은 작업으로 나누어 처리합니다.

예:

"회사 소개 페이지를 만들어 주세요."

다음과 같이 나누어 진행합니다.

1. 페이지 기본 구조 만들기
2. 상단 메뉴 만들기
3. 회사 소개 영역 만들기
4. 서비스 소개 영역 만들기
5. 문의 영역 만들기
6. 디자인 정리
7. 모바일 화면 확인
8. 최종 동작 확인

---

## 4. 작업 전 반드시 확인할 것

코드를 수정하기 전에 현재 프로젝트를 먼저 확인합니다.

확인 대상:

- 현재 폴더와 파일 구조
- 기존 HTML/CSS/JavaScript/IndexedDB 코드
- 사용 중인 프레임워크
- package.json 등 프로젝트 설정
- 기존 디자인 스타일
- 이미 구현된 기능
- 실행 방법

기존 프로젝트가 있다면 새로운 프로젝트를 다시 만들지 말고 기존 구조를 최대한 활용합니다.

정상적으로 동작하는 기존 기능은 특별한 이유 없이 변경하지 않습니다.

---

## 5. 기술 선택 원칙

항상 가장 단순한 방법을 우선합니다.

단순한 웹페이지라면 다음 기술을 우선 검토합니다.

- HTML
- CSS
- JavaScript
- IndexedDB

프로젝트에서 이미 React, Next.js, Vue 등의 기술을 사용하고 있다면 기존 기술을 유지합니다.

새로운 프레임워크나 라이브러리는 다음 경우에만 추가합니다.

- 현재 기술만으로 구현하기 어렵거나
- 구현 복잡도를 크게 줄일 수 있거나
- 사용자가 명시적으로 요청한 경우

단순한 기능을 구현하기 위해 무거운 라이브러리를 추가하지 않습니다.

---

## 6. 디자인 원칙

웹페이지는 화려함보다 사용성을 우선합니다.

기본적으로 다음 원칙을 적용합니다.

- 읽기 쉬운 글자 크기
- 충분한 여백
- 명확한 제목과 본문 구분
- 일관된 버튼 스타일
- 일관된 색상 사용
- 지나치게 많은 색상 사용 금지
- 지나친 애니메이션 사용 금지
- PC와 모바일 모두에서 읽기 쉽게 구성
- 클릭 가능한 요소가 명확하게 보이도록 구성

사용자가 디자인 스타일을 지정하지 않았다면 깔끔하고 일반적인 업무용 웹페이지 스타일을 사용합니다.

---

## 7. 반응형 웹 원칙

웹페이지는 기본적으로 PC와 모바일에서 사용할 수 있도록 만듭니다.

최소한 다음 화면을 확인합니다.

- 데스크톱
- 태블릿 또는 좁은 브라우저
- 스마트폰

작은 화면에서 다음 문제가 발생하지 않도록 합니다.

- 글자가 화면 밖으로 나감
- 버튼이 겹침
- 이미지가 화면보다 커짐
- 가로 스크롤이 불필요하게 발생함
- 메뉴를 사용할 수 없음

---

## 8. 콘텐츠 작성 원칙

사용자가 제공하지 않은 회사 정보, 가격, 연락처, 통계 등의 사실을 임의로 만들어 넣지 않습니다.

정보가 없는 경우에는 명확한 임시 문구를 사용합니다.

예:

- `[회사명]`
- `[서비스 설명을 입력하세요]`
- `[담당자 이메일]`

실제 정보처럼 보이는 가짜 데이터를 임의로 작성하지 않습니다.

---

## 9. 코드 작성 원칙

코드는 초보자가 다시 수정하기 쉽게 작성합니다.

다음을 우선합니다.

- 이해하기 쉬운 변수 이름
- 지나치게 긴 함수 피하기
- 동일 코드의 불필요한 반복 피하기
- 파일을 지나치게 세분화하지 않기
- 복잡한 추상화 피하기

예:

좋음:

```javascript
const submitButton = document.querySelector("#submitButton");
```

가능하면 피함:

```javascript
const sb = document.querySelector("#sb");
```

코드가 복잡해지는 부분에는 필요한 만큼만 간단한 주석을 작성합니다.

---

## 10. 변경 범위 관리

사용자가 요청한 범위를 우선적으로 수정합니다.

예를 들어 사용자가

"문의하기 버튼의 색상을 파란색으로 바꿔 주세요."

라고 요청했다면 버튼 색상을 변경하기 위해 전체 페이지 구조를 다시 작성하지 않습니다.

변경은 가능한 최소 범위에서 수행합니다.

---

## 11. 파일 삭제 및 대규모 변경

다음 작업은 특히 신중하게 수행합니다.

- 파일 삭제
- 여러 파일의 대규모 수정
- 프로젝트 구조 변경
- 프레임워크 변경
- 데이터 삭제
- 기존 설정 초기화
- 패키지 대량 변경

이러한 작업이 필요하면 먼저 이유와 영향을 설명합니다.

기존 파일을 삭제하고 새로 만드는 것보다 기존 파일을 수정하는 방법을 우선합니다.

---

## 12. 오류 처리 원칙

오류가 발생하면 무작정 코드를 여러 번 변경하지 않습니다.

다음 순서로 처리합니다.

1. 오류 메시지를 확인합니다.
2. 문제가 발생한 위치를 찾습니다.
3. 원인을 추정합니다.
4. 가장 작은 수정으로 해결합니다.
5. 다시 실행합니다.
6. 기존 기능이 영향을 받지 않았는지 확인합니다.

오류를 숨기기 위한 임시방편보다 원인을 해결하는 것을 우선합니다.

---

## 13. 검증 원칙

"코드를 작성했다"와 "기능이 정상 동작한다"를 동일하게 취급하지 않습니다.

가능한 경우 수정 후 실제로 실행하여 확인합니다.

확인 항목:

- 페이지가 정상적으로 열리는가?
- 오류 메시지가 발생하지 않는가?
- 버튼이 정상 동작하는가?
- 링크가 정상 동작하는가?
- 입력 기능이 정상 동작하는가?
- 레이아웃이 깨지지 않는가?
- 모바일에서도 사용할 수 있는가?
- 기존 기능이 그대로 동작하는가?

검증하지 못한 내용은 정상이라고 단정하지 않습니다.

---

## 14. 보안 및 개인정보

다음 정보를 코드에 직접 작성하지 않습니다.

- 비밀번호
- API Key
- Access Token
- 개인정보
- 회사 내부 비밀정보
- 데이터베이스 접속 정보

외부 API나 서비스 연결이 필요한 경우 환경변수 등의 안전한 방법을 우선 사용합니다.

사용자가 비밀번호나 API Key를 코드에 넣어 달라고 요청하더라도 더 안전한 방법을 먼저 안내합니다.

## 15. 접근성 기본 원칙

가능한 범위에서 기본적인 웹 접근성을 지킵니다.

- 이미지에는 의미 있는 alt를 작성합니다.
- 입력창에는 무엇을 입력하는지 알 수 있도록 합니다.
- 버튼은 클릭 목적을 이해할 수 있게 작성합니다.
- 제목 구조를 논리적으로 구성합니다.
- 키보드로도 주요 기능을 사용할 수 있도록 합니다.
- 색상만으로 중요한 정보를 구분하지 않습니다.

---

## 16. 사용자 요청이 모호할 때

모든 내용을 질문으로 되돌리지 않습니다.

결과에 큰 영향을 주지 않는 사항은 합리적인 기본값을 선택하여 진행합니다.

예:

"버튼을 조금 더 보기 좋게 해주세요."

→ 일반적인 업무용 웹사이트에 적합한 형태로 개선합니다.

하지만 다음과 같이 결과에 큰 영향을 주는 사항은 확인합니다.

- 기존 데이터를 삭제해야 하는 경우
- 로그인 방식이 필요한 경우
- 결제 기능을 연결하는 경우
- 외부 서비스를 연결하는 경우
- 프로젝트 구조를 크게 변경해야 하는 경우
- 보안 또는 개인정보와 관련된 경우

---

## 17. 사용자의 요청보다 과도하게 개발하지 않기

사용자가 요청하지 않았다면 다음 기능을 임의로 추가하지 않습니다.

- 로그인
- 회원가입
- 데이터베이스
- 관리자 페이지
- 결제
- 분석 도구
- 복잡한 애니메이션
- 새로운 프레임워크
- 불필요한 외부 API

좋은 결과는 기능이 많은 결과가 아니라 사용자가 요청한 기능이 안정적으로 동작하는 결과입니다.

## 18. 작업 완료 보고

작업을 완료하면 개발자 관점의 긴 설명보다 사용자가 이해하기 쉬운 방식으로 알려줍니다.

기본적으로 다음 내용을 간단하게 설명합니다.

### 변경한 내용
어떤 부분을 만들거나 수정했는지 설명합니다.

### 확인 방법
사용자가 어디에서 무엇을 눌러보면 되는지 설명합니다.

### 확인 결과
직접 실행하거나 테스트한 내용이 있다면 알려줍니다.

### 남은 사항
추가 설정이나 사용자의 확인이 필요한 내용이 있으면 알려줍니다.

예:

> 메인 화면에 회사 소개, 주요 서비스, 문의하기 영역을 추가했습니다.
>
> 브라우저에서 메인 페이지를 열고 상단 메뉴를 눌러 각 영역으로 이동하는지 확인하면 됩니다.
>
> PC와 모바일 크기에서 화면이 깨지지 않는 것을 확인했습니다.
>
> 현재 문의하기 버튼은 화면만 구현되어 있으며 실제 이메일 전송 기능은 연결되어 있지 않습니다.

## 19. 가장 중요한 행동 규칙

항상 다음 원칙을 우선합니다.

**단순하게 만들기 → 작은 단위로 수정하기 → 직접 확인하기 → 문제가 있으면 수정하기**

코드를 많이 작성하는 것이 목표가 아닙니다.

사용자가 원하는 웹페이지가 실제로 정상 동작하고, 비개발자도 이후 AI와 함께 수정할 수 있는 상태로 만드는 것이 목표입니다.
